# Next Rust

Next Rust gives Rust the Next.js App Router model. Folders under `app/` become routes, layouts nest, pages
render on the server, and `next-rust build` produces **one stripped binary** with the pages, config and static
files embedded — nothing else to deploy, no Node.js, no bundler.

If you know Next.js, most of your instincts transfer. What does *not* transfer: nothing is discovered at
runtime. A build script parses `app/` at compile time, so a wrong filename, a missing `pub`, a misspelled
export or an `async fn` where a sync one is required is a **build error**, not a 404 you debug later. That
strictness is the point — and it's why guessing names wastes more time than checking this skill.

## Orient yourself before editing

Two minutes here saves a rewrite. From the project root:

```sh
cat next-rust.toml          # which features are on: tailwind, rendering defaults, api prefix
next-rust routes --layouts  # every route, static vs dynamic, and WHY it is dynamic
ls app/                     # the routing tree is the source of truth
```

`next-rust routes` is the fastest way to confirm the framework understood your directory names. If the CLI
isn't installed, `cargo run -p next-rust-cli -- routes` inside the framework checkout does the same, and the
app binary itself accepts `--routes`.

Then decide which kind of work you're doing, because the rules differ:

| | You're building an app | You're changing the framework |
| --- | --- | --- |
| Signals | a project with `app/`, `next-rust.toml`, `next-rust` as a dependency | the workspace with `crates/next-rust-*`, `website/`, `examples/` |
| Read next | this file, then `references/app-api.md` | `references/framework-internals.md` |
| Verify with | `cargo build`, `next-rust routes`, `TestClient` tests | `cargo fmt` + `clippy -D warnings` + `cargo test --workspace` + `cargo doc` |

## Rules that will bite you if you skip them

These are the mistakes that cost real time, all of them mechanical:

1. **Export names are fixed.** `page.rs` exports `Page`, `layout.rs` exports `Layout`, `not-found.rs` exports
   `NotFound`, `route.rs` exports `GET`/`POST`/…, and `error.rs` exports **`ErrorBoundary`** (not `Error`).
   All must be `pub`. Wrong name → `NR0201`.
2. **`loading.rs`, `error.rs` and `global-error.rs` must be synchronous.** They render instantly while
   something else is pending, so an `async fn` is `NR0204`. Pages, layouts and loaders may be async.
3. **`load` must return `Result` and live in the same file as the export that consumes it.** The generated
   glue does `let data = load(..).await?;` then `Page(Data(data))`. A `load` returning a bare `T` doesn't
   compile, and a `load` in another module is simply never called.
4. **Adding or renaming a file under `app/` needs a rebuild**, not a reload — the route table is generated by
   `build.rs`. `next-rust dev` handles this for you; a plain `cargo run` does not pick up new files unless the
   build script reruns.
5. **Files under `app/` are modules of your crate**, included with `#[path]`. Reach your own code with
   `crate::` (`crate::db::posts()`), never with the crate's own name — `my_app::db` doesn't resolve there.
   Helper modules can live anywhere; only the special filenames become routes.
6. **Never edit generated code.** `$OUT_DIR/next_rust_routes.rs` and friends are build output. Fix the source
   or the build script.
7. **Unknown keys in `next-rust.toml` are hard errors** (`deny_unknown_fields`). A typo fails the build with
   the key name — don't invent config keys; check `references/cli-and-config.md`.
8. **Text is escaped for you.** `div!["<b>"]` renders escaped text. Only `raw_html` injects markup, and it
   must never receive user input. `on*` attributes passed to `attr()` are dropped on purpose; use `raw_attr`
   if you truly need one.
9. **Release builds rename Tailwind and UI component (`nr-*`) classes** to short random names and prune unused CSS.
   Scripts in `client/`/`assets/` are rewritten to match where a string is clearly a class list; a class built
   any other way (a JS string in Rust, a regex, third-party HTML) needs `[tailwind] keep_classes` or
   `[assets] css_safelist`. Don't "fix" a production-only styling bug by turning Tailwind off.
   Pages receive only the rules for classes they render plus those of the scripts they load: a class that
   only a script adds in a way the build can't see must be in `keep_classes`.
10. **Reach for `next_rust::ui` before hand-building controls.** Buttons, fields, select, date picker, toggles,
    avatars, cards and layout exist (`use next_rust::ui::*;`, see `references/app-api.md#ui-components`).
    Restyle them with `class(..)`; don't copy their markup.

## Building an app

The view DSL: every HTML tag is a macro. Parts are attributes or children, in any order, comma separated.
`class(..)` merges when repeated, `(value, condition)` includes a class conditionally.

```rust
use next_rust::prelude::*;

pub fn Page() -> impl View {
    main![
        class("mx-auto max-w-2xl px-6 py-16"),
        h1![class("text-3xl font-bold"), "Posts"],
        ul![each(POSTS, |p| li![a![href(format!("/blog/{}", p.slug)), p.title]])],
        when(POSTS.is_empty(), || p![class("text-zinc-500"), "Nothing here yet."]),
    ]
}
```

Element macros are named exactly after the tag — `time!`, `form!`, `label!`, `main!` — with one exception,
`use_!`, because `use` is a keyword. The trailing underscore belongs to *attribute* helpers whose name would
clash with Rust: `r#type`/`type_`, `r#for`/`for_`, `r#async`, `as_`, plus the renamed `form_attr`,
`label_attr`, `slot_attr`, `http_equiv`, `view_box`. So `time![datetime(post.date), post.date]` — never
`time_!`.

### Routes and layouts

```
app/layout.rs              → /            wraps everything (must render {children})
app/page.rs                → /
app/blog/page.rs           → /blog
app/blog/[slug]/page.rs    → /blog/:slug
app/docs/[...path]/page.rs → /docs/*      catch-all ([[...path]] also matches /docs)
app/(marketing)/about/page.rs → /about    (group) organises files, never appears in the URL
app/api/users/route.rs     → /api/users   JSON endpoints
```

```rust
// app/layout.rs — the root layout owns <body>'s content, not <html>
pub fn Layout(children: Children) -> impl View {
    div![header![nav![Link!(href = "/", "Home")]], main![children], footer!["© 2026"]]
}
```

### Loading data, 404s and redirects

```rust
// app/blog/[slug]/page.rs
use next_rust::prelude::*;

pub async fn load(params: Params) -> Result<Post> {
    let slug = params.get("slug").unwrap_or_default();   // Option<&str>, borrowed from the request
    posts::find(slug).await?.or_not_found()              // Option → 404 via the nearest not-found.rs
}

pub fn Page(Data(post): Data<Post>) -> impl View {
    article![h1![post.title.clone()], p![post.summary.clone()]]
}
```

`not_found()`, `redirect("/login")` and `permanent_redirect(..)` are `Error` values: return them with `?` or
`Err(..)` from `load`, a page, `metadata` or an action. `Error::validation([("email", "Invalid")])` is a 422
with per-field messages. `?` works with any `std::error::Error`.

Extractors go in the signature of `load`, `Page`, `metadata` or a middleware: `Params`, `Path<T>`, `Query<T>`,
`Headers`, `Cookies`, `Ctx`, `Extension<T>`, `Auth<T>`, `CsrfToken`, `FormState`, `RequestInfo`, `ClientIp`, `Nonce`.
**Only `Params`, `Path` and `Nonce` are static-safe** — any other extractor makes the page dynamic under
`[rendering] default = "auto"`, which is usually what you want, but check with `next-rust routes --layouts`
when you expected a page to be pre-rendered.

### API routes

```rust
// app/api/contact/route.rs
use next_rust::prelude::*;
use serde::{Deserialize, Serialize};

#[derive(Deserialize)]
struct NewMessage { name: String, email: String, message: String }

pub async fn POST(mut req: Request) -> Result<Json<Receipt>> {
    let body: NewMessage = req.json().await?;          // 2 MiB limit by default
    if !body.email.contains('@') {
        return Err(Error::validation([("email", "Enter a valid email address")]));
    }
    Ok(Json(store(body).await?))
}
```

A handler takes **no arguments or exactly one `Request`** (anything else is `NR0205`), may be sync or async,
and returns anything that implements `IntoResponse`: `Response`, `Json<T>`, `Html<T>`, `String`, `Bytes`,
`StatusCode`, `(StatusCode, T)`, `()` for 204, or `Result<T, E>`. `HEAD` and `OPTIONS` are answered for you.

### Forms and server actions

An action is a normal function; the macro publishes it at a hashed URL and the client runtime enhances the
form. It works without JavaScript too (POST + redirect), which is why validation errors come back as flash
state rather than only as JSON.

```rust
// src/actions.rs  (or anywhere in app/ or src/)
#[server_action]
pub async fn signup(input: Signup) -> Result<()> {
    if !input.email.contains('@') {
        return Err(Error::validation([("email", "Enter a valid email address")]));
    }
    users::create(input).await?;
    Err(redirect("/welcome"))
}
```

```rust
// in a page: FormState carries errors and submitted values after a no-JS round trip
pub fn Page(form: FormState) -> impl View {
    form![
        action!(crate::actions::signup),
        input![name("email"), value(form.value("email")), r#type("email")],
        small![data("nr-error", "email"), form.error("email").unwrap_or_default().to_owned()],
        input![r#type("hidden"), name("_redirect"), value("/welcome")],
        button![r#type("submit"), "Sign up"],
    ]
}
```

From JavaScript: `await window.nextRust.action(url, input)`. Actions are POST-only and reject cross-origin
requests.

Two things that quietly break a form like this:

- **`novalidate` on the form** when you want the server's message to be the one people see. Otherwise an
  `input![r#type("email")]` lets the browser block the submit with its own bubble, and your
  `data-nr-error` slot never fills.
- **The client runtime only ships to pages that need it** — a page with an internal link, an island, or an
  action form (action forms count from 0.1.8 on; on 0.1.7 put a `Link!` on the page). Without it a form
  submits with a full page load. That is why the no-JS path exists and why the `_redirect` field matters: the
  form keeps working either way.

### Interactivity without a client framework

`Link!` navigates without a reload (plain `a![href(..)]` to a local path does too). For small interactive
pieces, `#[client]` islands run a declarative runtime — no eval, strict-CSP safe:

```rust
#[client]
pub fn Counter(count: i32) -> impl View {
    div![
        button![on("click", "decrement:count"), "−"],
        span![data("nr-text", "count"), count.to_string()],
        button![on("click", "increment:count"), "+"],
    ]
}
```

Island arguments are serialized into the HTML as props, so they are public — never pass secrets. For real
client code, `#[client(module = "/_next-rust/client/x.js")]` loads an ES module exporting `hydrate(element, props)`.

### Styling

With `[tailwind] enabled = true` (the default for new projects) just write classes; the CSS for exactly the
classes you use is generated and inlined. Otherwise `global_css!("globals.css")` in the root layout, or
`css_module!("card.module.css")` for scoped classes (`styles.card_title`, a compile error if the class
doesn't exist). `asset!("fonts/inter.woff2")` returns a content-hashed URL.

### Static, dynamic and ISR

```rust
pub const RENDERING: Rendering = Rendering::Static;   // Static | Dynamic | Auto (default)
pub const REVALIDATE: u64 = 60;                       // seconds; serve stale, re-render in background
pub const TAGS: &[&str] = &["posts"];                 // for revalidate_tag("posts")

pub async fn generate_params() -> Vec<Params> {       // takes no arguments
    posts().await.into_iter().map(|p| Params::new().with("slug", p.slug.as_str())).collect()
}
```

`next_rust::revalidate_path("/blog/hello").await` and `revalidate_tag("posts").await` invalidate on demand.
For cached data, `cache(key, CacheOptions::revalidate(60).tag("posts"), || async { … }).await`.

## Verify what you built

Don't hand back unverified work; these are cheap:

```sh
cargo build                 # the real check: routing, signatures and codegen all run here
next-rust routes --layouts  # confirm the URL, the layout chain and static/dynamic
next-rust dev               # http://localhost:3000, rebuilds on change
next-rust build             # production: also pre-renders every static page, so prod-only panics surface
```

A test is better than a screenshot, and the framework ships a client for it:

```rust
#[tokio::test]
async fn blog_shows_a_post_and_404s_for_unknown_slugs() {
    let client = next_rust::TestClient::new(my_app::routes());
    let res = client.get("/blog/hello").await;
    assert_eq!(res.status, 200);
    assert!(res.text.contains("Hello"));
    assert_eq!(client.get("/blog/nope").await.status, 404);
}
```

`TestClient` also has `post_json`, `post_form`, `get_with_headers` and `navigate` (which simulates a
client-side navigation, including the partial-rendering headers). This needs `next_rust::routes!()` to be
reachable from a library target — put it in `src/lib.rs` and let `src/main.rs` call
`next_rust::run(my_app::routes())`.

## When the build fails

Errors come with a code and a `help:` line — read them, they name the fix. The frequent ones:

| Code | Meaning |
| --- | --- |
| `NR0201` | The file doesn't export the required `pub fn` (wrong name, missing `pub`). |
| `NR0204` | `Loading` / `ErrorBoundary` / `GlobalError` must not be `async`. |
| `NR0205` | Bad signature: API handlers take `Request` or nothing; `middleware` takes exactly `(Request, Next)`. |
| `NR0206` | That argument isn't allowed here (`Children` only in layouts/templates, `Data<T>` needs a `load` in the same file). |
| `NR0102` / `NR0104` | Two routes resolve to the same URL (page vs page, or page vs `route.rs`). |
| `NR0103` / `NR0107` | Conflicting or duplicate dynamic parameter names. |
| `NR0105` / `NR0116` | A catch-all must be the last segment; `[...x]` and `[[...x]]` can't be siblings. |
| `NR0108` | Invalid directory name — parameter names must be identifiers. |
| `NR0210` | A server action takes at most two arguments (`ActionContext`, input). |

`references/diagnostics.md` lists every code with the usual cause. `next-rust doctor` checks the environment
(toolchain, config, port, `.env` in `.gitignore`) when something looks wrong outside your code.

## Working on the framework itself

Ten crates with a strict dependency direction: `next-rust-build` and `next-rust-cli` must never end up in an
application binary, `next-rust-view` stays server-independent, `next-rust-assets` keeps **zero** dependencies.
Before pushing, run what CI runs:

```sh
cargo fmt --all
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --all-features
cargo +1.89 check --workspace --all-features    # CI's MSRV job, easy to forget
```

Several things in this repo are booby-trapped for the unwary: the browser runtime exists twice (readable and
minified) behind a source-hash test, documentation lives in Rust files under `website/src/content/`, the
version is owned by release automation, and the website is built with the framework itself, so a breaking
change fails CI there. **Read `references/framework-internals.md` before touching `crates/`.**
